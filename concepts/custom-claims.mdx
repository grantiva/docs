---
title: "Custom Claims"
description: "Add your own data to attestation JWT tokens"
---

Custom claims let you embed additional data in the JWT returned by attestation. Your backend reads these claims to make authorization decisions without extra API calls.

## Claim types

| Type | `claim_type` | Description | Available on |
|------|--------------|-------------|--------------|
| **Static** | `static` | The same fixed value for every device | All plans |
| **Conditional** | `conditional` | A value chosen by rules over device properties — risk score, jailbreak status, attestation count | Pro and above |
| **Dynamic** | `dynamic` | A value computed from an expression over the device profile | Pro and above |
| **External** | `external` | Fetched from your own API at attestation time | Enterprise only |

Data types are `string`, `number`, `boolean`, `array`, `object`, and `date`.

<Note>
The Free plan allows **static claims only**. Creating a conditional, dynamic, or external claim on Free returns a 403.
</Note>

<Note>
`subscription` is a **reserved claim key**, managed by Grantiva's [subscription entitlement ingestion](/concepts/subscription-claims). Creating a custom claim named `subscription` — in any casing — returns a 400.
</Note>

## Tier limits

| Plan | Max active claims | Types allowed |
|------|------------------:|---------------|
| Free | 1 | Static |
| Pro | 5 | Static, conditional, dynamic |
| Business | 10 | Static, conditional, dynamic |
| Enterprise | 20 | Static, conditional, dynamic, external |

The limit counts **active** claims only — deactivating a claim frees a slot without deleting it.

## Managing claims

### Dashboard

Go to **Custom Claims** in the Configure section of the sidebar. From there you can add a claim, edit one, reorder them, and delete. Each claim carries a key, display name, description, data type, priority, and type-specific configuration.

Claim types your plan doesn't include are shown with a plan badge and raise an upgrade prompt when selected.

### API

Claims are managed over `/api/v1/org/claims`, authenticated with an [organization API key](/api-reference/org/api-keys) or a dashboard session. Wire keys are `snake_case`.

```bash
curl -X POST https://api.grantiva.io/api/v1/org/claims \
  -H "Authorization: Bearer aat_YOUR_ORG_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "claim_key": "user_tier",
    "claim_name": "User Tier",
    "claim_type": "static",
    "data_type": "string",
    "static_value": "premium"
  }'
```

| Endpoint | Purpose | Required scope |
|----------|---------|----------------|
| `GET /api/v1/org/claims` | List claims in priority order | `claims:read` |
| `POST /api/v1/org/claims` | Create a claim | `claims:write` |
| `PUT /api/v1/org/claims/:ref` | Update a claim | `claims:write` |
| `PUT /api/v1/org/claims/reorder` | Set evaluation order | `claims:write` |
| `DELETE /api/v1/org/claims/:ref` | Delete a claim | `claims:delete` |
| `POST /api/v1/org/claims/test` | Evaluate an unsaved definition | `claims:test` |
| `POST /api/v1/org/claims/:ref/preview` | Evaluate a saved claim | `claims:test` |

`:ref` accepts either the claim's UUID or its claim key.

<Warning>
`claim_key`, `claim_type`, and `data_type` are **immutable** after creation. To change any of them, delete the claim and create a new one.
</Warning>

See the [Custom Claims API reference](/api-reference/claims) for the full field list.

## Evaluation order

Claims are evaluated in ascending `priority`, then by key. A claim whose evaluation fails or produces no value is **silently dropped from the token** — it never fails the attestation. Your backend should treat a missing claim as a normal case.

## Reading claims

In the attestation result:

```swift
let result = try await grantiva.validateAttestation()

if let tier = result.customClaims["user_tier"] as? String {
    print("User tier: \(tier)")
}
```

And in the decoded JWT on your backend:

```json
{
  "custom_claims": {
    "user_tier": "premium",
    "restricted": false
  }
}
```

<Warning>
The `customClaims` map in the HTTP response is a flat string-to-string map — nested objects are stringified. For structured claims such as `subscription`, read the **decoded JWT** instead.
</Warning>

## Testing claims

Preview how a claim evaluates without performing a real attestation:

```bash
curl -X POST https://api.grantiva.io/api/v1/org/claims/test \
  -H "Authorization: Bearer aat_YOUR_ORG_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "claim": {
      "claim_key": "restricted",
      "claim_name": "Restricted",
      "claim_type": "conditional",
      "data_type": "boolean",
      "conditional_rules": { "...": "..." }
    },
    "context": {
      "device": {
        "risk_score": 75,
        "jailbreak_detected": true,
        "device_model": "iPhone15,2",
        "os_version": "18.0",
        "country": "US"
      }
    }
  }'
```

The response gives you `claim_key`, `evaluated_value`, `data_type`, `evaluation_time_ms`, and any `errors`. `POST /api/v1/org/claims/:ref/preview` takes just the `context` object and evaluates the saved claim.

Testing bypasses tier claim limits, but testing an external claim still requires Enterprise — evaluation makes a real outbound call to your configured endpoint.
