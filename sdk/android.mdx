**Not yet available.** The Android SDK is in development and has not been published. There is no Maven or Gradle coordinate to depend on yet, and no release to install. This page describes the shape it is taking so you can plan around it — everything here may change before the first release.

Want it sooner, or want to try a pre-release build? [Email us](mailto:support@grantiva.io).

The Android SDK is the counterpart to the iOS SDK's App Attest flow. Your app proves it is genuine and unmodified through [Google Play Integrity](https://developer.android.com/google/play/integrity), Grantiva verifies that proof, and your backend receives the same kind of attestation JWT it already knows how to check.

No API key is embedded in your release app — the Play Integrity verdict is the authentication.

## Scope: attestation only

The first release covers attestation and device intelligence. It does not include feature flags, feedback and support tickets, push token registration, or user identity. Don't plan an Android release around those.

| Capability | iOS (2.1.0) | Android |
|------------|:-----------:|:-------:|
| Attestation → JWT | Yes | Planned |
| Device intelligence / risk score | Yes | Planned |
| Feature flags | Yes | No |
| Feedback + support tickets | Yes | No |
| Push token registration | Yes | No |
| User identity (`identify`) | Yes | No |

## Planned requirements

- **minSdk 23** — `EncryptedSharedPreferences` requires API 23+
- compileSdk 34, JDK 17
- Google Play Services on the device for a real Play Integrity verdict

## What attestation will return

The same three-band risk model the iOS SDK uses, derived from the Play Integrity verdict rather than App Attest:

| Field | Description |
|-------|-------------|
| `token` | JWT — send as `Authorization: Bearer <token>` |
| `expiresAt` | ISO-8601 expiry timestamp |
| `deviceIntelligence.deviceId` | Pseudo-anonymous identifier for this installation |
| `deviceIntelligence.riskScore` | 0–100. Null on the Free tier, present on Pro and above |
| `deviceIntelligence.riskCategory` | `trusted` (0–20), `suspicious` (21–75), `blocked` (76–100). All tiers |
| `deviceIntelligence.isEmulator` | True when the verdict indicates a virtual device |
| `deviceIntelligence.attestationCount` | Times this device has attested |
| `deviceIntelligence.lastAttestationDate` | ISO-8601 date of the previous attestation, null on the first |

See [risk scoring](/concepts/risk-scoring) for how the bands map to decisions on your backend.

## The device ID will not be hardware-bound

This is the one place Android differs materially from iOS, and it affects billing.

On iOS the device identity derives from a Secure Enclave key, so it survives app reinstalls. On Android there is no equivalent, so the device ID is a UUID held in encrypted app storage. It is not hardware-bound, which means:

- A fresh install produces a **new** device ID
- The new ID counts as a new device against your [Monthly Active Devices](/dashboard/billing) quota

Plan for the JWT's device identifier to be stable per install, not per handset.

## In the meantime

If you ship on both platforms, start with the [iOS SDK](/sdk/installation) — the JWT your backend verifies is the same shape, so the [backend verification](/backend-verification) work carries straight over when Android lands.
